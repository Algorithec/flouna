## KNOWN FAILURES REMAINING

1. **Sealed-holdout misses: 38/382 (9.9%).** By first failing field:
   `ride.pickup` 6, `ride.vehicle` (combo) 6, `food.priority` 5,
   `ride.maxPickupMinutes` 4, `food.item` 3, `food.domain` (short noun → OOS) 3,
   `food.dietary` (combo) 3, `food.dietary` 2, `shop.priority` 2,
   `greeting.domain` 1, `ride.priority` 1, `shop.category` 1.
2. **Contradictory source labels** account for roughly half of those misses:
   phantom `ride.pickup` values (corpus leaves null for "ke liye" phrasing,
   holdout expects a value), combo `vehicle` split between `cab`/`any`/`auto`
   for the same sentence shape, one ride fixture demanding literal lowercase
   casing, ETA-vs-priority label noise, and dish-implied dietary labels that
   differ across splits. These cap this holdout at ~94–96%.
3. **Ride extraction** is the weakest family: 85.6% on the sealed holdout
   (18/125 misses), mostly pickup/vehicle/schedule fields inside combos.
4. **Priority without a domain noun**: "find me something affordable", "what is
   the fastest option", "I don't want to wait" are answered `out_of_scope`
   rather than a price/speed food request (MLX manual probes; the Q8 Ollama
   artifact produced invalid `domain:"price"` / `domain:"speed"` for two of
   them).
5. **Item echo**: "I want pizza" sets `item` to "I want pizza" instead of
   "pizza" (MLX manual probe; the Q8 artifact returns "pizza").
6. **Sealed injection miss 1/3** (`h-inj-01`) emits `domain:"admin"`, a schema
   violation — not a greeting and not a leak.
7. **Sealed greeting miss 1/12**: one greeting is answered as `out_of_scope`.
8. **32-prompt Ollama battery**: 32/32 parse, 29/32 schema-valid; the three
   misses are the price/speed enum slips above plus one long combo sentence
   that adds a stray `reply` key inside `ride` and omits `priority`.
9. **Action domain (integration gap, not a V5 training error)**: the current
   production prompt defines a seventh `action` domain (cart, group order,
   selection, settings, navigation) that is absent from V4/V5 data and from all
   fixtures. Under that prompt V5 scores 92.9% on fixtures (105/113, 111/113
   schema-valid) versus 94.7% with the prompt it was trained on.
10. **V4-era eval set (`eval_mlx.jsonl`, 540 rows)** scores 52.8% fully right,
    expected: it asserts old near-null conventions from the V4 taxonomy, while
    domain accuracy is 99.3% and JSON validity 99.8%.

### OLD / NEW / REASON (documented in `model/configs/*.yaml`)

- **run 1 vs V4** — OLD: 5,400 rows, 200 steps. NEW: 10,166 rows, 600 steps
  planned. REASON: the V5 corpus is ~1.9× larger and adds OOS, dietary and
  priority coverage; the step count keeps the same per-sample exposure.
- **run 2 vs run 1** — OLD: lr 2e-4 over 600 from base, unweighted corpus. NEW:
  lr 1e-4 over 400, resumed from run 1, duplicate-free 864-row targeted
  curriculum. REASON: targeted refinement must not destroy the run-1 model;
  400 steps × batch 4 ≈ 1.9 passes over the curriculum.
- **run 3 vs run 2** — OLD: lr 1e-4 over 400, 864 rows. NEW: lr 6e-5 over 250,
  481 rows. REASON: a low-LR third pass for the last narrow phrasings — it
  regressed (see Iteration history) and was rejected.
- No change was made to rank, scale, dropout, target layers, batch size or
  sequence length; the adapters stack across runs.

## GGUF export

The repository's documented export path is Unsloth's
`save_pretrained_gguf` in `model/train_colab.py`, which requires CUDA and could
not run on this machine. The two local alternatives were checked and do not
support this model:

- `mlx_lm fuse --export-gguf` supports only llama/mixtral/mistral in the
  installed version (Qwen2 is rejected).
- Ollama's safetensors importer rejects `Qwen2ForCausalLM`
  ("unsupported MLX architecture").

A direct converter was therefore written: `model/export_gguf_v5.py` builds a
Qwen2 GGUF with `gguf.GGUFWriter` (architecture `qwen2`, 28 blocks, 1536 hidden,
8960 FFN, GQA 12/2, RoPE 1e6, ε 1e-6, tokenizer `gpt2` with pre `qwen2`,
151936 tokens, chat template, BOS 151643 / EOS 151645). Matrices are F16; norms
and biases are F32, matching upstream conversions (llama.cpp's RMSNorm cannot
mix F32/F16). The result is quantized with `llama-quantize … Q8_0`.

Verification:

| Check | Result |
|---|---|
| Tensor count / names | 338 / 338 mapped, llama.cpp loads all |
| F16 vs fused weights | max abs diff 2.98e-8 |
| Q8_0 vs fused weights | max abs diff 5.4e-3 (expected quantization error) |
| Tokenizer parity | "cheap biryani under 200" → ids `[61690, 15248, 88, 5559, 1212, 220, 17, 15, 15]`, same as HF |

## Integration gap (for the team, not changed here)

The current `server/src/modules/chat/llm/prompt.ts` defines a seventh `action`
domain (cart, group order, selection, settings, navigation) with a large nested
schema. That domain is absent from the V4/V5 data and from the repo fixtures;
`results/data_analysis.md` already records that no action accuracy is claimed.
Against that prompt V5 scores 105/113 (92.9%) on fixtures with 111/113
schema-valid, versus 94.7% with the 402-token prompt it was trained on. Using
V5 in production therefore requires either the 6-domain prompt V5 was trained
on, or a V6 trained on action data with fixtures for it (fixtures currently
contain zero action cases).
