# Dataset analysis — V4 vs V5

All numbers below are measured from the files in `model/`, not from older
reports. V5 was generated by `gen_data_v5.py` (seed 20261110) and checked with
`validate_dataset.py`.

| train | 5,400 | 10,166 |
| validation | 540 (`eval_mlx.jsonl`) | 281 (`valid_mlx_v5.jsonl`) |
| held-out | — | 382 (`eval_mlx_v5.jsonl`) |

## Domains

| Domain | V4 train | V5 train | V5 valid | V5 holdout |
|---|---:|---:|---:|---:|
| food | 1,525 | 4,572 | 203 | 175 |

| combo | 261 | 461 | 0 | 20 |
| greeting | 23 | 32 | 0 | 12 |
| out_of_scope | 23 | 75 | 0 | 20 |

V4 had 23 OOS and 23 greeting rows; that thin coverage is the most likely
source of the OOS→greeting failure. V5 has 75 OOS rows, including explicit hard
negatives (weather, cricket, quantum computing, Python, jokes, translations,
airplanes, Elon Musk, capital of Japan) and 32 greetings that are not OOS.

| Label | V4 train | V5 train | V5 valid | V5 holdout |
|---|---:|---:|---:|---:|
| priority price | 939 | 1,432 | 46 | 53 |
| priority speed | 903 | 2,490 | 88 | 113 |
| priority rating | 694 | 1,146 | 28 | 27 |

| dietary nonveg | 73 | 1,034 | 54 | 45 |
| dietary any | 1,679 | 2,230 | 63 | 61 |

V4 had only 107 explicit dietary labels across 1,525 food rows, which is why
the stored V4 report showed 50% dietary accuracy on the tuned set and 40% on
the holdout. V5 adds 2,803 explicit dietary labels and keeps the canonical
enum (`veg` / `nonveg` / `any`) only.

Canonical-cue coverage in V5 training rows:

- 1,706 rows contain a price cue (cheap / affordable / budget / low cost /
  inexpensive / lowest price / save money) and 783 food rows carry
  `priority:"price"`.
- 1,058 rows contain a speed cue (fast / quick / quickly / ASAP / minimum wait /
  don't want to wait / jaldi) and 1,428 food rows carry `priority:"speed"`.
- 968 rows contain a non-veg cue (non-veg / non vegetarian / chicken / mutton /
  meat / fish / prawn / egg); 1,034 food rows carry `dietary:"nonveg"`.
- 777 rows contain a veg cue; 1,769 food rows carry `dietary:"veg"`.
- 75 rows are out_of_scope; 25 of them contain a recognisable hard-negative
  topic word.

## Validation and leakage

`validate_dataset.py` result: **PASS, 0 hard failures**.

- Every row is a chat object with system/user/assistant, the assistant content
  parses as JSON, validates against the production schema (nested objects,
  canonical enums, no extra keys) and has no text/label conflict (budget,
  delivery time, pickup wait, clock time).
- Exactly one system prompt text per split (the 402-token training prompt).
- Exact duplicate user+label rows: 0 in all three splits.
- Near duplicates (4-gram Jaccard ≥ 0.90): 1 warning in train
  ("uttapam jaldi" / "jaldi uttapam", same label). Kept; the pair is a
  deliberate word-order paraphrase, not a contradictory duplicate.
- Cross-split exact overlap: train∩valid 0, train∩eval 0, valid∩eval 0.
- Train/valid/eval ∩ repo fixtures: 0.
- V4 repairs applied before adding rows: 130 typo rows dropped, 60 phantom
  budgets cleared (amount cue came from a delivery-time phrase), 20 trip times
  wrongly copied into `maxPickupMinutes` cleared. 5,270 of 5,400 V4 rows kept.
- 62 generated holdout rows and 22 train / 18 valid rows were removed because
  they duplicated a fixture or another split.

## Data-quality notes

- V5 does not repeat V4's five known failure patterns: no synonym enum values,
  no flat objects, no typo injection, no label contradicting the sentence.
- The `action` domain from the production schema is not present in either the
  V4 data or the repo fixtures. V5 does not add it; the metric reports below
  therefore do not claim action accuracy.
- The task spec lists an older intent taxonomy (information / discovery /
  decision / clarification). The current production schema and fixtures use
  domains instead, so "intent" is reported as domain classification.
